## 三、耦合分析：挪动会挂的 5 类根源

1. **ROOT 深度约定**：多数脚本 `ROOT = dirname(dirname(abspath(__file__)))`（2 级上=仓库根）。**文件每深移一层，就必须把这个 dirname 深度 +1**，否则 grow3/`调参产物` 找不到。
2. **同目录 import（自洽簇）**：`tune_engine` 簇 5 个工具、`run_full_union` 簇 2 个工具，都靠 `sys.path.insert(0, dirname(__file__))` 找同目录共享库。**整簇搬 = 内部自洽**，代价只在"簇内唯一算 ROOT 的那个文件"。
3. **根锚点**：`grow3/`、`corpus.csv`、`config.json`、`exp/golden`、`调参产物/` 被几乎所有脚本按 ROOT 引用 → **一律不动**。
4. **顶层脚本被 import**：`grow.py`←(verify/tune_bind/probe_words)、`interactive_cloud.py`←(eval_versions/legacy)、`regress.py` 锚 exp/golden → **顶层脚本留在根**。
5. **bat 入口**：`run*.bat` 用 `cd /d "%~dp0"` + `python -m grow3.cli` → 必须留在根。

**结论：乱的主要是"文档/数据/报告平铺"与"两个自洽工具簇没归组"，不是引擎层。可低成本归整。**

## 六、验证方案（挪完不挂的证明流程）

每个阶段提交前、后都要跑：

1. **基线先行**（S1 前）：记录 `python -m grow3.cli` 冒烟、`python regress.py` ALL PASS、signal_bank 三件套（verify_plan 18/18、verify_dashboard 全过、verify_random 23/23）的当前输出。
2. **每阶段移动后**：
   - `git status` 核对移动清单（`git mv`，无遗留）
   - 所有被移动 .py：`python -m py_compile <file>` 逐一编译通过
   - **import 冒烟**（关键）：一次性脚本，分别插入 `调参工具/参数搜索`、`调参工具/全量交并`，逐个 import 簇内全部模块（依赖 grow3 的靠各自修正后的 ROOT 自举）
   - **功能冒烟**：
     - 簇 A：`python -c "from tune_engine import Engine"` + 任一工具 `--help`
     - 簇 B：`python 调参工具/全量交并/dump_signals.py`（重生成 v1 信号表到 调参产物/，秒级）

4. **回滚**：每个阶段单独 `git commit`，任一环节挂 → `git revert` 该阶段即可，不影响其它阶段。

## 八、可行性结论

**能，且成本低。** 依据：
1. "乱"的主体是**文档/数据/报告平铺**（可零风险归组）与**两个自洽工具簇没归组**——不是引擎层问题。
2. 两个簇都是"同目录 import 自洽"结构：**整簇搬 = 内部互不破坏**，唯一要改的是簇内"算 ROOT 的那个文件"的 dirname 深度（共 5 行）+ signal_bank 3 行联动 = **约 7 行代码改动**。
3. 所有根锚点（grow3/config/corpus/bat/exp/golden/调参产物/out）**一律不动** → 主链路（run_all.bat、regress、CLI）零影响。
4. 每组都有 `git commit + 冒烟 + regress` 双保险，S1 零风险先做，后续每一步都可独立回滚。
5. 风险点唯一在 S4（signal_bank 3 文件的 import 路径），但该包自带 3 套验收脚本，跑一遍即证。

**不建议做的**：把 `grow.py` 等 5 个顶层脚本挪进子目录（需联动改 4+ 处 import，收益小）；把 exp/ 再细分（已是历史分区且 golden 是 regress 硬依赖）；动 `调参产物/`、`out/`（gitignored 产物，工具按 ROOT 引用）。
